# Transfer approval lookup and first catalogue-scale measurement

The transfer repeatedly copied immutable approved reference keys into each live
reference snapshot, then prepared per-row membership queries. New frozen reviews
now contain `TransferApprovedLookup`. A snapshot can attach that held review with
`mode=ro&immutable=1` and run the same membership and disappeared-row predicates
inside SQLite. A separate file lease denies writes/rename until the attachment
is closed. This optimization changes lookup work, not the number or authority of
fresh reference captures, writer locks, receipts or original-file checks.

URI decoding is enabled only on this scratch connection, using an optional
constructor flag whose default remains false. No process-wide SQLite setting is
changed. Unicode and URI-special filename bytes are encoded. Existing reviews
without the index, UNC paths and work paths of 240 or more characters retain the
previous disk projection. Network and long-URI opening are not newly assumed.

The two set queries install a scoped thread-local cancellation callback and
restore the preceding callback on every exit. Interruption is translated back
to a safe stop; reserve-check errors keep their message. The source review stays
immutable and live catalogue/personal references are still recaptured before
both original-removal boundaries.

SQLite's [URI documentation](https://www.sqlite.org/uri.html) specifies the
connection flag, attached-database behavior and read-only mode. The review is a
sealed DELETE-journal database held against changes, as required for immutable
access; this option is not used on mutable collection databases.

## Measured scale point

The new benchmark builds 100,003 synthetic book rows on G: referencing two tiny
private ZIP carriers. It measures catalogue/reference work, not large-archive
throughput. It compares all eight selected primary book fields on every row
(identity, library ID, title, filename, extension, member index, size and deleted
flag), and independently hashes both moved carriers. Derived Search* fields are
allowed to be regenerated by the normal locator triggers.

The same benchmark script SHA-256
`4e175043dedf50a57077fd839d8d491df552a27ee0d15ac9e4060452b21b45e8`
produced:

| Run | Native seconds | Sampled additional file allocation |
| --- | ---: | ---: |
| Baseline r1152, previous committed implementation | 120.078 | 353,979,728 bytes |
| Final r1164 | 95.937 | 351,997,264 bytes |

This timing pair is 20.104% faster. Both have five complete live reference
captures; the final run uses five held read-only attachments and no approval
table copies. Row hashes and byte-exact carrier checks pass, and both runtimes
were removed. Sampling uses FILE_STANDARD_INFO allocation sizes about every
0.5 seconds; these are observed file-allocation peaks, excluding directory/MFT
overhead, not exact volume peaks or a hard admission guarantee. C: keeps an 8 GiB
reserve and all test/temp/output data stays on G:. Background machine load is not
controlled, so this one pair is not a universal speed claim.

The replaced per-row lookup variant r1159 passed safety checks but took 123.219 s;
it was not accepted as an acceleration. Earlier r1150/r1151 failed benchmark
setup/comparison (missing required fields, then empty derived search keys), not
application data preservation. r1151's first footprint helper queried compressed
file size; its results are not used as allocation evidence. Compile r1153 missed
the driver's explicit unit import; its failure is retained, not a passing gate.
