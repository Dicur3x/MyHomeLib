# OpenXPS catalogue preview and conversion

OXPS now uses the Windows XPS Object Model to prepare an in-memory legacy XPS
package for the existing WPF renderer. The raw source stays read-only, including
when the catalogue holds its selected-book lease. The first-page request removes
later native page references before preparing images or serializing the temporary
package; whole-book conversion retains every page. No normalized file is saved.

The bridge requires Windows 8 or newer with the XPS Document API. If the API is
unavailable, the catalogue explains that requirement. This path was checked with
a controlled missing-API response, not on an actual Windows 7 machine. The
existing optional XPS module, cancellation, 30-second deadline, 384 MiB child
commit limit and 600-pixel cover bound still apply. The native output stream has
an additional 256 MiB bound. Selecting a book never installs a component.

The whole source is validated before native parsing, including later pages,
external relationships and active markup. Embedded resource dictionaries, fonts
and PNG images retain their intended page appearance. JPEG XR image resources
are prepared through the Windows JPEG-XR-to-HD-Photo API before legacy rendering.
OpenXPS keeps the standard `application/vnd.ms-package.xps-*+xml` part types and
`image/vnd.ms-photo` for JPEG XR; changing these MIME types to invented OXPS/JXR
types produces an invalid package.

The managed COM declarations use SDK interface order and documented GUIDs. The
SDK headers used to inspect that order are bound by SHA256 in the evidence.
Relevant primary references are the
[package factory](https://learn.microsoft.com/en-us/windows/win32/api/xpsobjectmodel_1/nf-xpsobjectmodel_1-ixpsomobjectfactory1-createpackagefromfile1),
[package writer](https://learn.microsoft.com/en-us/windows/win32/api/xpsobjectmodel_1/nf-xpsobjectmodel_1-ixpsompackage1-writetostream1),
[JPEG XR conversion](https://learn.microsoft.com/en-us/windows/win32/api/xpsobjectmodel_1/nf-xpsobjectmodel_1-ixpsomobjectfactory1-convertjpegxrtohdphoto)
and [ECMA-388](https://www.ecma-international.org/wp-content/uploads/ECMA-388_1st_edition_june_2009.pdf).

WPF resolves resources through a unique registered in-memory package URI. Without
that registration it reopened original OXPS child parts despite the normalized
root, producing an unknown-FixedDocument error. The registered package now owns
the resource namespace throughout rendering and is removed on disposal; both
legacy XPS and OpenXPS pass through this route.

## Evidence

`G:/HL-b14-external/oxps-cover-validation-r1361/summary.json` binds the current
source/test hashes, native executable hashes and PE architectures, helper runtime
manifests, SDK headers and image/font fixtures. It is a focused cohort, not a
complete production-app input manifest.

- Win64 r1357 and Win32 r1358 each pass 18 focused methods: 16 native-preview
  methods and two existing conversion methods. OXPS checks cover first-page
  pixels, full-render order, resource dictionaries, embedded PNG/JPEG XR,
  embedded glyph shapes, later-page active markup, external relationships,
  excessive page counts, unavailable API and a damaged later page that must not
  be prepared for a cover-only request. Legacy cancellation, source sharing,
  truncated input, CRC/output bounds and missing-module checks remain covered.
- Actual catalogue panel runs r1359/r1360 each pass six XPS/OXPS checks: both
  standalone formats, both inside ZIP, damaged latest selection without stale
  pixels, and a missing module. On those same binaries, 16 Kindle, 47 raw package,
  15 package-panel and four asynchronous FB2 checks also pass: 176 panel/regression
  checks across both architectures. These are separate from the 36 methods above.
- The final consolidation performs four whole-converter outputs: OXPS to FB2 and
  EPUB with each helper architecture. It independently checks both pages' order
  and colors, preserved source SHA256 and removal of temporary conversion data.
  These four outputs are not additional unittest methods.
- Every private native/UI/pipeline runtime is removed, real Kindle fixture hashes
  are unchanged, and all processing uses G:. C: retains its 8 GiB reserve; E: is
  unused. No Desktop installation or public package was changed.

For reproduction, the native suite uses the variables listed in the earlier
[XPS audit](2026-11-17-xps-cover-preview.md), plus `HL_XPS_FONT` pointing to an
installed font and `HL_XPS_JXR` pointing to a JPEG XR fixture. The latter can be
generated by compiling `tools/bookconvert/tests/xps_resource_fixture.cs` against
WindowsBase, PresentationCore and System.Xaml in an owned G: folder. Build the
fake helper from the current `xps_cover_fixture.cs`, which includes the controlled
unavailable-API response. Actual panel tests use `--modes xps-preview --xps-dir`.

Early probes with invalid content types, a missing System.Xaml fixture reference
and missing in-memory WPF registration failed before the final cohort. They are
diagnostic attempts, not passing gates. Both separate image-only helpers were
rebuilt from the shared C# source and their runtime hashes checked; image-processing
algorithms did not change. Final component packages must use a new XPS component
version and matching source hashes rather than overwrite the published 3.0.0.5
asset. Final Main builds and release installation remain open. These synthetic
fixtures on the current Windows host do not establish every real OXPS producer,
older operating systems, KFX/AZW8, legacy Kindle HTML covers or pure vector SVG.
