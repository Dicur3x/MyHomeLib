# Library update sources: model checkpoint

The settings model in `unit_LibraryUpdateSources.pas` now represents a local/network folder or HTTP/HTTPS base, index/version file names, full/delta mode, enabled state, book root and optional stable `TCatalogSource.ID` binding. Every profile has its own GUID. Renaming its display name leaves the GUID/binding unchanged. JSON version 1 rejects invalid IDs, duplicate IDs, unknown schemas, traversal and drive-relative/current-drive folder paths. Profiles are stored with the collection rather than matched to its display name; the settings-window checkpoint below covers that integration.

The legacy importer reads physical lines instead of INI keys so repeated keys cannot erase profiles. On the user's supplied `collections.ini`, all 11 update descriptions survive, both `Update9` entries remain distinct, and the undefined `Group5` is diagnosed. Individual source locations are preserved. The extra INPX creation templates are inspected for group diagnostics but are not silently installed/rewritten. Legacy export retains the original first six fields and adds stable profile/source IDs, book root and enabled state for the new reader; JSON/INI roundtrips preserve those fields. Older readers do not understand the new binding/enabled fields, so export is not a promise of identical automatic dispatch in an older application.

`LibraryUpdateSourcesTest` ran successfully on x86 and x64 with the real supplied file, which remained byte-exact. ## Index acquisition checkpoint

`unit_LibraryUpdateFetch.pas` now prepares an owned, frozen index snapshot from a local/network folder or HTTP/HTTPS endpoint. The original is opened read-only with writes denied while copying; the staged result remains read-locked and has a SHA-256 witness. Remote filenames are encoded by path segment, and HTTP errors are rejected. Transfers check cancellation, the 8 GiB system reserve, 512 MiB workspace margin and a 1 GiB input ceiling. The private directory is held open and resolved through its handle. Cleanup removes its own index and only an empty directory; unexpected files are retained.

The actual native implementation passed on x64 (`G:/HL-b14-external/index-fetch-Win64-r212/report.json`, 1.781 s) and x86 (`G:/HL-b14-external/index-fetch-Win32-r214/report.json`, 1.546 s). Both ordinary Unicode paths and paths of 343 characters are checked: exact local/remote bytes, original and staged write leases, cancellation, HTTP 404, an individual base URL with escaped Unicode/spaces, retention of unexpected staged data, retention of other cache files, and owned cleanup. All fixtures were private copies on G: and were removed. These runs do not constitute a real library import, UI flow, TLS/server authentication matrix or a hard-crash orphan-cleanup check.

## Settings window checkpoint

The normal collection menu now opens `Настроить источники обновлений…`. The new runtime form edits a profile's location, index/version names, book-folder hint, full/delta mode, enabled state and merged-source binding. Settings are committed atomically in the collection's `Settings` table under `PROP_LIBRARY_UPDATE_SOURCES`, so collection rename does not break them. Import/export supports JSON and legacy INI. Imported entries are initially disabled for review rather than all being treated as updates of the current collection; import alone does not overwrite the saved settings. Inline instructions and the local `?` button explain this flow. Reports use a label/copy action rather than an editable text input.

`Проверить файл` runs the actual staged-index transport in the existing background progress window. It checks availability/transfer, not yet the index's book-level meaning. Switching the selected profile or editing/importing settings releases the prior snapshot. A separate logical selection survives VCL list-handle recreation during theme/DPI changes; the first integration run exposed and fixed that issue.

Native full-application fixtures passed on x64 (`G:/HL-b14-external/source-settings-ui-Win64-r219/catalogue-Win64-apply.json`, 38.344 s) and x86 (`G:/HL-b14-external/source-settings-ui-Win32-r221/catalogue-Win32-apply.json`, 56.890 s). They use the real editor controls, catalogue settings, progress window and collection-menu entry: editing retains IDs, saving survives a collection rename, local transport freezes exact original bytes, import invalidates/cleans the snapshot, both duplicate INI entries and group warnings appear, imported templates remain disabled, export retains bindings and reviewing an INI does not auto-save it. Text/button layout and theme switching are checked at 96/144/192/240/288 DPI in both themes. Unrelated test archives and original INPX remain unchanged; private runtimes were removed. These checks cover this settings/file-acquisition window, not the final update-preview/application UI, all monitor layouts or final visual inspection.
